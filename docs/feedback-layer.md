# 反馈层：两个 mode 的五类问题

该层接入现有意图解析、任务计划、字段执行和 PDF 导出。正常轮次只增加本地检查和至多 3 条已审阅经验，不增加模型调用。没有新建一个每轮运行的 LLM critic，也没有自动改模型权重。

## 运行位置与行为

| 问题 | 当前实现 | 验证边界 |
| --- | --- | --- |
| 已回答的问题再问 | 开放待办绑定字段、阶段和设计指纹；成功提交后保存回答证据。发现相同有效待办则撤下，阻止历史恢复重新创建它。连续三次同问同状态停止追问，保留可写绑定。 | 字段存在本身不能证明已回答；建议、批准及前提发生变化的待办不能自动关闭。 |
| 跨阶段修改失效 | 现有执行器负责字段修改；反馈层对已提交目标字段建立检查点，在后续草稿生成覆盖这些字段时恢复一次，再由统一投影产生页面内容。 | 不把未知历史意图当作修改授权；只能恢复本轮已提交的明确目标字段。 |
| 元问题不回应 | 沿用两个 mode 的只读元问题路径；混合消息中的明确、未引用元问题补进独立任务，在提交修改后本地回答。 | 引号内的实验标题等内容不是元问题；无法确定的自由表达仍需现有语义解析。 |
| 多请求只处理一项 | 按每个问题的回答回执完成任务，不能用一个响应类型把所有问题标为完成；批次单项服务失败保留其他成功回答。用户反馈漏答时，补答有记录的未完成问题。 | 回执证明调用产出了非空且未标为未完成的回答，不代表已经证明物理解释正确。 |
| 对话、状态与 PDF 不一致 | 学生报告和 Builder 输入均带设计版本及规范字段指纹；Builder 导出前检查研究问题、变量、基准、假设/趋势/边界和数值方案的实际值是否对应当前状态。 | 指纹标识规范设计输入，并非 PDF 文件哈希；字段校验不等于全文语义或 Unity 运行验收。 |

用户可直接说“我已经回答过了”“之前改的没有生效”“你没有回答我的问题”“PDF 内容和对话不一致”。纯反馈不会推进阶段或写入实验字段。带有修改、物理问题的混合消息继续走现有任务拆分路径，不被反馈快捷路径吞掉。

已确认回答仅在当前设计指纹仍匹配时有效。采用保守的全设计依赖失效方式，避免新前提下沿用旧确认；这可能比字段级依赖更保守，但不会替用户批准新方案。

漏答恢复复用现有问题回答器，每批至多处理 16 个问题；每项在同一设计指纹下只允许一次反馈补答尝试。失败项继续标为待处理，不无限调用模型。请求超过已有批次限制的部分保留待答。其他类型的漏做任务保留在记录中，不伪造完成。

## 经验如何指导模型

`src/ece329_workflow/feedback.py` 内的 `RULES` 是随代码审阅发布的五条通用经验，两个 mode 共用。现另从 SQLite 中检索维护者已启用的经验：按 mode、阶段筛选，以反馈类别或关键词匹配，最多取 3 条；无匹配不注入。`guidance()` 合并动态经验与内置规则，总计至多 3 条、650 字符正文。经验仅影响提示上下文，确定性的状态检查仍由代码执行。

同一检索结果结构 `feedback_guidance` 进入：

1. `dialogue_state.serialize_intent_input()`：辅助拆分用户请求。
2. `prompts.build_prompt_packet()`：辅助生成回复及检查已提交状态。

经验是辅助规则，不能覆盖当前用户明确要求、课程边界、审批状态和规范字段值。经验编号及诊断记录不要求学生阅读。

## 候选经验与维护

每个会话在 `model_context.feedback` 保存：

- `events`：至多 50 条去重候选记录，含类别、mode、阶段、版本、证据、出现次数、处理结果和规则版本。
- `answers`：至多 50 条已提交回答证据。
- `last_pending`：无进展检测计数。
- `last_tasks`：最近任务的逐项结果。
- `unanswered_tasks`：至多 50 项未答问题，普通后续轮次不会清空；得到回答回执后移除。
- `question_retries`：至多 50 个补答尝试标识。

候选记录只说明用户报告或本地检查发现了什么；`needs_review` 不等于确认系统有错。用户反馈原文不会被检索为模型指令，也不会自动升级为全局经验。SQLite 部署随会话持久保存；内存 store 重启后不保留。

维护者可从实际部署数据库只读导出某个会话的候选证据。在仓库根目录 CMD 执行（替换为实际数据库和 design-id）：

```bat
set PYTHONPATH=src
python -m tools.export_feedback_candidates --database "实际数据库文件.sqlite" --design-id "实际设计ID" --output "build\feedback-candidates.json"
```

导出只包含该会话的候选证据，不包含访问令牌或完整会话。该命令不会创建、清理或写入源数据库。

上述会话内诊断仍可用命令行导出。新增的显式反馈提交采用下面的在线维护流程；代码缺陷仍应修复代码并补回归，不能仅靠经验提示解决。正常设计参数留在会话和审阅证据中，不应进入通用规则正文。

## 反馈提交、分析、审阅、检索的完整线路

1. **用户提交**：工作台右上角“反馈问题”及每条在线回答下方“反馈这条回答 / Report Problem”，两个 mode 共用。选择五类问题之一或“其他”，输入问题并选择会话、项目或全局候选范围；本地示例不可提交。反馈不会调用设计 turn 或推进阶段。成功提示必须收到后端回执，网络异常保留草稿、目标和 `request_id`；原内容重试不重复建单。
2. **保存证据**：`POST /v1/designs/{id}/feedback` 使用该设计的 Bearer 令牌，返回记录 ID、状态、设计版本和持久化标识。保存反馈及服务器截取的当前规范字段（最多 8000 字符）和最近 4 轮对话（每轮用户 1500、助手 2000 字符），不读取客户端自报证据，不保存访问令牌。可传 `revision/stage` 标记历史回答，服务器从历史中匹配该轮原文摘录（用户 1500、助手 4000 字符），无法匹配时显式记录为空；未指定 stage 时按目标版本的历史 handled_stage 定位；记录 reported_mode 与提交时 mode，跨阶段或切换 mode 后不冒用当前归属。同时保存目标前一轮、目标轮、后一轮的事件链（各轮用户最多 2000、助手 4000 字符）及可用的前后阶段、待确认事项、字段来源记录。新产生的对话捕获状态；旧历史缺少的状态标为 null，不以当前状态补造。当前快照与历史目标分开。`telemetry_id` 必须属于该设计，供评测记录关联。
3. **后台分析**：复用配置好的在线模型/transport，每次分析尝试最多两次严格 JSON Schema 调用：先生成证据诊断与候选（输出上限 4200 tokens），再检查证据支持及正反例（1400 tokens）；不沿用设计对话的模型 response ID。反馈是分析数据，不能直接成为模型指令。无在线模型或解析失败时保留记录并显示失败，不阻塞设计。证据不足或检查未通过时记录 `no_learning`，不生成可启用经验。诊断、检查结果保存在反馈记录的 `extraction_analysis` 中；候选审阅页可展开查看。模型案例检查不是实际工作流回放，标记固定为 `not_replayed`，不自动循环修复。
4. **审阅**：打开 `feedback-review.html`，输入独立维护者令牌，读取原始证据和历史审阅记录，核对/编辑候选 JSON，选择修正字段，依次填写原不恰当内容、人工修改后的正确内容、对经验层 Agent 所总结经验的处理意见，再启用或不采用。启用时后台将修正内容写入所选字段；其余字段以 JSON 为准。已启用经验可停用，停用后可重新启用。未审阅内容不进入检索；版本冲突返回 409，需刷新后核对。文本全用 `textContent`/表单值渲染。
5. **指导设计**：每轮意图解析前和提交/阶段切换后的回复生成前，重新检索当前 mode、阶段、消息适用的已启用经验；补答也携带已检索经验。规则按 `EXP-...` ID 和版本进入既有 `feedback_guidance`，不要求学生阅读编号。启用/停用影响后续轮次，不追溯修改已经生成的回复、设计或 PDF，不会改模型权重、公式库或业务代码。

| 接口 | 权限 | 用途 |
| --- | --- | --- |
| `POST /v1/designs/{id}/feedback` | 设计 Bearer | `{message, category, request_id, revision?, stage?, scope?, telemetry_id?}`；新建 201，幂等重放 200 |
| `GET /v1/designs/{id}/feedback` | 设计 Bearer | 最近 100 条反馈、处理状态、可否重试 |
| `POST /v1/designs/{id}/feedback/{ticket}/retry` | 设计 Bearer | 仅重试失败且少于 10 次尝试的分析（含备用 API 尝试）；返回 202 |
| `GET /v1/feedback/tickets?status=failed&offset=0` | `X-ECE329-Feedback-Admin-Token` | 全部反馈收件箱，status 可省略；返回各状态数量和总数，每页 50 条 |
| `GET /v1/feedback/tickets/{ticket}` | 同上 | 查看保存的对话证据、候选、检查结果及各次分析诊断 |
| `POST /v1/feedback/tickets/{ticket}/retry` | 同上 | 维护者重试失败任务，沿用同一 10 次总额度，不推进设计 |
| `GET /v1/feedback/experiences?status=candidate&offset=0` | `X-ECE329-Feedback-Admin-Token` | 分页读取经验及证据，每页 50 条 |
| `POST /v1/feedback/experiences/{experience}/review` | 同上 | `{decision: approve/reject/disable/delete, version, note: {field, original, corrected, opinion}, content?, scope?}`；记录原值、修正值与审阅历史 |

状态为 `queued → running → candidate → active/rejected`，`active → disabled → active`。分析也可结束于 `no_learning`、`duplicate` 或 `failed`。结构合法不等于语义正确，各范围的 `candidate` 均须维护者验证后才启用。去重同时考虑规范内容和会话/项目/全局范围，避免不同用户的会话经验互相覆盖。审阅页可编辑范围；`delete` 软删除并保留审计，不再检索，也不能直接重新启用。

会话经验仅作用于来源 design，项目经验按后端 `ECE329_PROJECT_ID` 隔离，全局经验仍须审核。旧记录保持原有全局候选/审核语义；项目范围是当前没有用户账户体系时的实现，并不代表已增加个人账户经验库。每次只取 Top 3 相关 active 规则。关闭“使用已审阅经验”会清空检索结果；关闭开关或启用规则 ID/版本改变时重建远端模型上下文，防止旧规则残留。本地确定性校验和五类内置问题诊断一直启用。策略、范围与评测设置见 [实施说明](routing-experience-implementation.md)。

队列保存在与设计相同的 SQLite 文件中，任务租约至少为 300 秒，并按配置的模型超时延长以容纳草案和检查两次调用；进程重启会恢复排队任务、回收过期租约。旧 worker 的迟到结果不能覆盖新任务。单条反馈最多 10 次分析尝试，首次分析、自动切换 API、人工重试及租约回收均共用这个计数。连接失败、超时、配置错误或 HTTP 拒绝时，在同一任务中按允许列表顺序尝试另一个已配置服务商的第一个模型（OpenAI/DeepSeek 各至多一个），不在模型间无限轮换。输出解析失败不自动切换；证据不足仍记为 no_learning。服务商都失败或额度用尽时停止；尚有额度可由用户或维护者重试。异常恢复中已达到 10 次的 queued 任务也直接转为 failed，避免后台永久空轮询。每设计最多 100 条反馈。页面每 5 秒刷新待处理状态，最多连续 60 次，关闭窗口停止轮询，可手动刷新。无任务时后台线程退出，新反馈会唤醒线程。需要长期运行的 WSGI 服务；不依赖外部任务队列，不适用于执行后立即冻结进程的 serverless 环境。

提交或重试分析与旧列表请求重叠时，页面会在旧请求结束后合并执行一次新读取，避免已保存记录被旧列表隐藏。后台连续三次存储异常后退出，任务继续保留；维护者修复数据库后，后续请求或服务重启可重新启动处理。日志记录异常，不能把存储故障解释为模型已完成分析。

使用内存 store 时页面明确提示“重启后丢失”；生产必须挂载持久磁盘。删除设计或 SQLite 会话 TTL 清理时，同时删除关联反馈、经验和审阅证据；对应规则停止参与后续检索。故障时保留通用内置检查，经验库暂时不可读不应阻塞设计。

## 部署与实际验收

后端 `.env.production` 配置：

```dotenv
ECE329_DATABASE_PATH=/data/ece329.sqlite3
ECE329_FEEDBACK_ADMIN_TOKEN=在后端设置独立的随机长令牌
# 在线模型沿用既有 OPENAI_API_KEY / OPENAI_MODEL / ECE329_GENERATOR 配置
```

不要把模型密钥或维护者令牌写入 `docs/assets/config.js`、GitHub Pages、仓库或用户会话。静态前端仅配置后端 URL，审阅页复用同一 URL。现有 CORS 白名单需包含 Pages 所在 origin；接口已允许维护者令牌请求头。令牌仅留在审阅页内存，点击“清除令牌”清空。重启后端使配置和新路由生效，再发布 Pages 静态文件。

验收：用户提交一条带具体证据的反馈 → 检查回执 ID 与记录列表 → 等待模型分析为“待审阅” → 维护者核对内容及适用范围，填写验证依据并启用 → 在匹配 mode/阶段的新轮次检查实际回复 → 停用后确认后续轮次不再检索该规则。另应测试网络超时原内容重试、无权限审阅、模型失败的有限重试及服务重启后的记录恢复。审阅页说明验证依据，不会自动执行代码测试；经验有效性仍需真实模型回放。

## 人工修订如何改进经验提炼

审阅表单固定为：

1. 选择字段：`summary`、`trigger`、`recommendation` 或 `verification`。
2. **Agent 原不恰当内容**：展示该字段服务器存储的原文，不能凭记忆改写。
3. **人工修改后的正确内容**：填写修正后的完整字段；无需修改时复制原文。
4. **对经验层 Agent 总结的经验的处理意见**：至少 5 个字符，说明应如何修改、保留、限定适用范围或不予采用，以及总结方式应如何改进；可附验证依据，未回放时如实说明。实际启用、拒绝、停用等状态由操作按钮决定，不根据意见文字自动执行。

例如原摘要错误归因为“用户没有填写必要项目”，修正摘要应写“上一轮邀请确认继续，用户确认后却未推进”。处理意见写“修改后采用；归因应改为未承接确认，只适用于上一轮明确邀请确认继续的情形。已核对这三条对话，未执行回放”。不要把推测写成已证实根因。

新审阅提交结构化 `note: {field, original, corrected, opinion}`；旧结构化 `basis` 字段兼容读取并规范为 `opinion`，不清除历史记录。旧版自由文本审阅仍可读取，但不推测其原文/修正版，也不会自动成为提炼示例。后台校验原文和版本，冲突返回 409。拒绝、停用和删除也记录这一格式，但不将其修正直接写入规则；只有批准才应用所选字段的修正；其他操作携带 content 或 scope 时后端拒绝，避免隐式改写。切换修正字段时，已填内容同步到 JSON，启用时一并保存；JSON 格式错误则保持当前字段及修订草稿。

后台每次开始分析新反馈时，检索最多 3 条相关的已启用修订，附到 `reviewed_corrections`。检索遵守会话/项目/全局范围、mode、阶段、类别和关键词；候选、未采用、已停用、已删除、无改动或旧自由文本记录均不作为示例。示例按审阅前后的实际差异生成，changes 包含同次审阅各字段的有效修订，包括 JSON 编辑；已被后续改写的旧修订不再引用。示例仅携带修订字段、原文、正确内容、处理意见及适用条件，不附带来源用户的原始对话。维护者仍需确认通用经验及处理意见不含个人信息。

提炼先还原事件链，再区分证据事实、用户报告、预期、推测及未知项，明确规则条件和例外，最后构造正反案例并进行独立模型检查。审阅修订用于改进后续同类总结，不修改模型权重，不回写旧候选；已经开始的分析使用开始时检索的示例。停用后新分析不再取该示例。原稿的模型检查不等于人工修改后的规则已经重新验证。

本次升级无需新增环境变量，继续使用后端默认在线模型和 `ECE329_FEEDBACK_ADMIN_TOKEN`。需要同时部署前后端并重启后端；旧审阅页提交旧格式会收到要求刷新页面的错误。SQLite 沿用既有表结构，不清空数据。后台反馈分析独立于学生对话额度；每次分析最多两次模型调用，总计最多 10 次分析尝试（正常情况下最多 20 次模型调用），自动切换同样计数，无额外无限重试。

审阅页的摘要是概述；实际注入设计提示的字段为 trigger/recommendation/verification，修正摘要时需同步核对规则正文。后台提炼的 4200/1400 输出上限也传给 DeepSeek 适配层，不再被提供商的默认额度下限覆盖。


## 反馈收件箱与 API 故障切换（2026-09-18）

维护者页面默认展示“全部反馈”，区别于“待审阅经验”：分析失败、排队、未提炼经验以及重复经验都会保留在列表中。展开记录可查看证据、模型检查结果和 `analysis_attempts`；通过“查看关联经验”按精确 ID 进入审阅。列表不批量传输完整对话证据。

失败诊断仅记录 provider、model、阶段、错误类别及 HTTP 状态，不保存 API 密钥、原始异常正文或上游响应正文。`model_connection_error` 表示连接故障，`model_timeout` 表示超时，`model_rate_limited` 通常对应 HTTP 429，`model_request_rejected` 需要结合 HTTP 401/403/404 等状态检查鉴权、模型权限或名称，`model_output_invalid` 表示输出未通过解析或结构校验。余额充足不能排除这些故障。旧失败记录没有历史诊断时，更新后重试才能记录具体分类，不能据此倒推出旧失败原因。

连接被重置、远端提前断开、响应体传输不完整也归入连接故障并进入有限切换；即使 HTTP 错误正文读取中断，仍保留 HTTP 状态用于诊断。维护者列表从同一数据库快照读取总数、状态计数、当前页和关联经验，避免多进程写入时出现“有记录却计数为 0”或错误分页。

无需新增环境变量。继续配置 `OPENAI_API_KEY`、`DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`（已有默认值）及 `ECE329_ALLOWED_MODELS`；允许列表必须包含两个服务商可用的模型，才能跨服务商切换。首选仍为后端默认模型，备用按允许列表顺序选择，不会修改学生选择的对话模型。`OPENAI_TIMEOUT_SECONDS`、`DEEPSEEK_TIMEOUT_SECONDS` 控制各自超时。审阅需要 `ECE329_FEEDBACK_ADMIN_TOKEN`，持久化需要 `ECE329_DATABASE_PATH` 指向持久磁盘。

同时部署前端和后端后，原有 2/3 或 3/3 的失败记录会显示为 2/10、3/10，可直接重试，无需重复提交；不会自动消耗旧失败记录的剩余额度。前端优先显示后端返回的 `max_attempts`，兼容尚未升级的旧后端时仍显示其原 3 次限制。只更新前端时，全部反馈接口会明确提示需要升级后端。
