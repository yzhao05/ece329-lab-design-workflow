# 反馈层：两个 mode 的五类问题

该层接入现有意图解析、任务计划、字段执行和 PDF 导出。正常轮次只增加本地检查和至多 3 条已审阅经验，不增加模型调用。没有新建一个每轮运行的 LLM critic，也没有自动改模型权重。

## 运行位置与行为

| 问题 | 当前实现 | 验证边界 |
| --- | --- | --- |
| 已回答的问题再问 | 开放待办绑定字段、阶段和设计指纹；成功提交后保存回答证据。发现相同有效待办则撤下，阻止历史恢复重新创建它。连续三次同问同状态停止追问，保留可写绑定。 | 字段存在本身不能证明已回答；建议、批准及前提发生变化的待办不能自动关闭。 |
| 跨阶段修改失效 | 现有执行器负责字段修改；反馈层对已提交目标字段建立检查点，在后续草稿生成覆盖这些字段时恢复一次，再由统一投影产生页面内容。 | 不把未知历史意图当作修改授权；只能恢复本轮已提交的明确目标字段。 |
| 元问题不回应 | 沿用两个 mode 的只读元问题路径；混合消息中的明确、未引用元问题补进独立任务，在提交修改后本地回答。 | 引号内的实验标题等内容不是元问题；无法确定的自由表达仍需现有语义解析。 |
| 多请求只处理一项 | 按每个问题的回答回执完成任务，不能用一个响应类型把所有问题标为完成；批次单项服务失败保留其他成功回答。用户反馈漏答时，补答有记录的未完成问题。 | 回执证明调用产出了非空且未标为未完成的回答，不代表已经证明物理解释正确。 |
| 对话、状态与 PDF 不一致 | 学生报告和 Builder 输入均带设计版本及规范字段指纹；Builder 导出前检查研究问题、变量、基准、假设/趋势/边界和数值方案的实际值是否对应当前状态。 | 指纹标识规范设计输入，并非 PDF 文件哈希；字段校验不等于全文语义或 Unity 运行验收。 |

用户可直接说“我已经回答过了”“之前改的没有生效”“你没有回答我的问题”“PDF 内容和对话不一致”。纯反馈不会推进阶段或写入实验字段。带有修改、物理问题的混合消息继续走现有任务拆分路径，不被反馈快捷路径吞掉。

已确认回答仅在当前设计指纹仍匹配时有效。采用保守的全设计依赖失效方式，避免新前提下沿用旧确认；这可能比字段级依赖更保守，但不会替用户批准新方案。

漏答恢复复用现有问题回答器，每批至多处理 16 个问题；每项在同一设计指纹下只允许一次反馈补答尝试。失败项继续标为待处理，不无限调用模型。请求超过已有批次限制的部分保留待答。其他类型的漏做任务保留在记录中，不伪造完成。

## 经验如何指导模型

`src/ece329_workflow/feedback.py` 内的 `RULES` 是随代码审阅发布的五条通用经验，两个 mode 共用。现另从 SQLite 中检索维护者已启用的经验：按 mode、阶段筛选，以反馈类别或关键词匹配，最多取 3 条；无匹配不注入。`guidance()` 合并动态经验与内置规则，总计至多 3 条、650 字符正文。经验仅影响提示上下文，确定性的状态检查仍由代码执行。

同一检索结果结构 `feedback_guidance` 进入：

1. `dialogue_state.serialize_intent_input()`：辅助拆分用户请求。
2. `prompts.build_prompt_packet()`：辅助生成回复及检查已提交状态。

经验是辅助规则，不能覆盖当前用户明确要求、课程边界、审批状态和规范字段值。经验编号及诊断记录不要求学生阅读。

## 候选经验与维护

每个会话在 `model_context.feedback` 保存：

- `events`：至多 50 条去重候选记录，含类别、mode、阶段、版本、证据、出现次数、处理结果和规则版本。
- `answers`：至多 50 条已提交回答证据。
- `last_pending`：无进展检测计数。
- `last_tasks`：最近任务的逐项结果。
- `unanswered_tasks`：至多 50 项未答问题，普通后续轮次不会清空；得到回答回执后移除。
- `question_retries`：至多 50 个补答尝试标识。

候选记录只说明用户报告或本地检查发现了什么；`needs_review` 不等于确认系统有错。用户反馈原文不会被检索为模型指令，也不会自动升级为全局经验。SQLite 部署随会话持久保存；内存 store 重启后不保留。

维护者可从实际部署数据库只读导出某个会话的候选证据。在仓库根目录 CMD 执行（替换为实际数据库和 design-id）：

```bat
set PYTHONPATH=src
python -m tools.export_feedback_candidates --database "实际数据库文件.sqlite" --design-id "实际设计ID" --output "build\feedback-candidates.json"
```

导出只包含该会话的候选证据，不包含访问令牌或完整会话。该命令不会创建、清理或写入源数据库。

上述会话内诊断仍可用命令行导出。新增的显式反馈提交采用下面的在线维护流程；代码缺陷仍应修复代码并补回归，不能仅靠经验提示解决。正常设计参数留在会话和审阅证据中，不应进入通用规则正文。

## 反馈提交、分析、审阅、检索的完整线路

1. **用户提交**：工作台右上角“反馈问题”及每条在线回答下方“反馈这条回答 / Report Problem”，两个 mode 共用。选择五类问题之一或“其他”，输入问题并选择会话、项目或全局候选范围；本地示例不可提交。反馈不会调用设计 turn 或推进阶段。成功提示必须收到后端回执，网络异常保留草稿、目标和 `request_id`；原内容重试不重复建单。
2. **保存证据**：`POST /v1/designs/{id}/feedback` 使用该设计的 Bearer 令牌，返回记录 ID、状态、设计版本和持久化标识。保存反馈及服务器截取的当前规范字段（最多 8000 字符）和最近 4 轮对话（每轮用户 1500、助手 2000 字符），不读取客户端自报证据，不保存访问令牌。可传 `revision/stage` 标记历史回答，服务器从历史中匹配该轮原文摘录（用户 1500、助手 4000 字符），无法匹配时显式记录为空；当前快照与历史目标分开。`telemetry_id` 必须属于该设计，供评测记录关联。
3. **后台分析**：复用配置好的在线模型/transport，单条任务一次严格 JSON Schema 提炼，输出上限 2200 tokens；不沿用设计对话的模型 response ID。反馈是分析数据，不能直接成为模型指令。无在线模型或解析失败时保留记录并显示失败，不阻塞设计。证据不足时记录 `no_learning`，不生成经验。
4. **审阅**：打开 `feedback-review.html`，输入独立维护者令牌，读取原始证据和历史审阅记录，核对/编辑候选 JSON、填写验证依据，再启用或不采用。已启用经验可停用，停用后可重新启用。未审阅内容不进入检索；版本冲突返回 409，需刷新后核对。文本全用 `textContent`/表单值渲染。
5. **指导设计**：每轮意图解析前和提交/阶段切换后的回复生成前，重新检索当前 mode、阶段、消息适用的已启用经验；补答也携带已检索经验。规则按 `EXP-...` ID 和版本进入既有 `feedback_guidance`，不要求学生阅读编号。启用/停用影响后续轮次，不追溯修改已经生成的回复、设计或 PDF，不会改模型权重、公式库或业务代码。

| 接口 | 权限 | 用途 |
| --- | --- | --- |
| `POST /v1/designs/{id}/feedback` | 设计 Bearer | `{message, category, request_id, revision?, stage?, scope?, telemetry_id?}`；新建 201，幂等重放 200 |
| `GET /v1/designs/{id}/feedback` | 设计 Bearer | 最近 100 条反馈、处理状态、可否重试 |
| `POST /v1/designs/{id}/feedback/{ticket}/retry` | 设计 Bearer | 仅重试失败且少于 3 次尝试的分析；返回 202 |
| `GET /v1/feedback/experiences?status=candidate&offset=0` | `X-ECE329-Feedback-Admin-Token` | 分页读取经验及证据，每页 50 条 |
| `POST /v1/feedback/experiences/{experience}/review` | 同上 | `{decision: approve/reject/disable/delete, version, note, content?, scope?}`；记录审阅历史 |

状态为 `queued → running → candidate → active/rejected`，`active → disabled → active`。分析也可结束于 `no_learning`、`duplicate` 或 `failed`。结构合法不等于语义正确，各范围的 `candidate` 均须维护者验证后才启用。去重同时考虑规范内容和会话/项目/全局范围，避免不同用户的会话经验互相覆盖。审阅页可编辑范围；`delete` 软删除并保留审计，不再检索，也不能直接重新启用。

会话经验仅作用于来源 design，项目经验按后端 `ECE329_PROJECT_ID` 隔离，全局经验仍须审核。旧记录保持原有全局候选/审核语义；项目范围是当前没有用户账户体系时的实现，并不代表已增加个人账户经验库。每次只取 Top 3 相关 active 规则。关闭“使用已审阅经验”会清空检索结果；关闭开关或启用规则 ID/版本改变时重建远端模型上下文，防止旧规则残留。本地确定性校验和五类内置问题诊断一直启用。策略、范围与评测设置见 [实施说明](routing-experience-implementation.md)。

队列保存在与设计相同的 SQLite 文件中，任务租约为 300 秒；进程重启会恢复排队任务、回收过期租约。旧 worker 的迟到结果不能覆盖新任务。单条反馈最多 3 次分析尝试；普通失败不自动循环，只允许用户显式重试。每设计最多 100 条反馈。页面每 5 秒刷新待处理状态，最多连续 60 次，关闭窗口停止轮询，可手动刷新。无任务时后台线程退出，新反馈会唤醒线程。需要长期运行的 WSGI 服务；不依赖外部任务队列，不适用于执行后立即冻结进程的 serverless 环境。

提交或重试分析与旧列表请求重叠时，页面会在旧请求结束后合并执行一次新读取，避免已保存记录被旧列表隐藏。后台连续三次存储异常后退出，任务继续保留；维护者修复数据库后，后续请求或服务重启可重新启动处理。日志记录异常，不能把存储故障解释为模型已完成分析。

使用内存 store 时页面明确提示“重启后丢失”；生产必须挂载持久磁盘。删除设计或 SQLite 会话 TTL 清理时，同时删除关联反馈、经验和审阅证据；对应规则停止参与后续检索。故障时保留通用内置检查，经验库暂时不可读不应阻塞设计。

## 部署与实际验收

后端 `.env.production` 配置：

```dotenv
ECE329_DATABASE_PATH=/data/ece329.sqlite3
ECE329_FEEDBACK_ADMIN_TOKEN=在后端设置独立的随机长令牌
# 在线模型沿用既有 OPENAI_API_KEY / OPENAI_MODEL / ECE329_GENERATOR 配置
```

不要把模型密钥或维护者令牌写入 `docs/assets/config.js`、GitHub Pages、仓库或用户会话。静态前端仅配置后端 URL，审阅页复用同一 URL。现有 CORS 白名单需包含 Pages 所在 origin；接口已允许维护者令牌请求头。令牌仅留在审阅页内存，点击“清除令牌”清空。重启后端使配置和新路由生效，再发布 Pages 静态文件。

验收：用户提交一条带具体证据的反馈 → 检查回执 ID 与记录列表 → 等待模型分析为“待审阅” → 维护者核对内容及适用范围，填写验证依据并启用 → 在匹配 mode/阶段的新轮次检查实际回复 → 停用后确认后续轮次不再检索该规则。另应测试网络超时原内容重试、无权限审阅、模型失败的有限重试及服务重启后的记录恢复。审阅页说明验证依据，不会自动执行代码测试；经验有效性仍需真实模型回放。

## 回归

原反馈层已做全量及专项回归，并对学生/Builder PDF 的版本行和页面边界做过渲染检查。新增完整线路的回归入口如下；测试结果以实际运行输出为准。

`tests/test_feedback_layer.py` 覆盖两个 mode 的提交证据、依赖失效、候选保护、历史恢复、防重复、跨阶段恢复、混合元问题、逐题完成、部分失败、有限补答、规则检索、SQLite/候选导出和 Builder 值一致性。

```bat
set PYTHONPATH=src
python -m pytest -q -p no:cacheprovider tests/test_feedback_layer.py
python -m pytest -q -p no:cacheprovider tests/test_feedback_pipeline.py
node --test tests/frontend/feedback.test.cjs
```

`test_feedback_pipeline.py` 验证真实 API 鉴权、SQLite 持久化、幂等、模型 transport 契约、候选隔离、审阅版本/去重、两个 mode 的提示注入、停用撤回、重启租约恢复和删除；模型返回使用受控测试输出。前端测试执行实际提交状态和事件处理代码，覆盖重试、跨设计迟到回执、轮询停止及文本渲染。

可选浏览器联调使用 `tests.feedback_smoke_server` 与 `tools/verify_feedback_browser.cjs`，需要本机 Playwright 和可用浏览器。先运行 `python -m tests.feedback_smoke_server --database .test-tmp/feedback-browser.sqlite`，再把打印的本机 URL 传给 `node tools/verify_feedback_browser.cjs http://127.0.0.1:端口`。可用 `ECE329_SMOKE_BROWSER` 指定本机浏览器可执行文件；截图输出到 `.test-tmp/feedback-browser/`。每次使用新的测试数据库；该 fixture 使用公开测试令牌和模型替身，仅供本机联调，不能部署。

发布后需重启实际服务；GitHub push 本身不保证后端已更新。离线模型替身和本地浏览器联调不能代替部署后的真实模型验收，也不代表执行过 Unity。
