# 工作台翻译失败修复

截图能够确认前端进入翻译失败状态，不能单凭截图判断服务商最初返回的是超时、拒绝请求还是无效内容。本地检查确认：旧前端捕获任何翻译异常后停止队列，并将所有尚未翻译的正文替换为相同错误提示；具体诊断没有展示。

修改：

- 等待和失败时保留原文，页面仅显示一条状态说明和原有手动重试按钮。成功译文继续缓存，不修改会话和设计数据。
- DeepSeek 翻译使用非思考模式，不继承对话的思考预设；对话生成设置不变。减少思考占用翻译输出预算的风险。
- 工作台及维护者页面的翻译请求改为每批最多 6000 字符，长文本继续按安全边界分段，降低长批次截断风险。
- 后端保留输出截断、结构无效、残留中文、数值/引用变动的固定错误分类；前端提供中英文说明。服务商故障沿用已有安全分类，不显示原始请求、密钥或错误正文。
- 不新增自动重试或模型修复调用；失败后由用户手动重试。两种工作流共用相同实现。
- 更新页面静态资源版本号，避免部署后继续使用旧缓存。

验证：

- `tests/test_language_and_localization.py` 与 `tests/test_deepseek_provider.py`：60 passed，包含两种模式、四种 DeepSeek 模型/预设、鉴权、缓存、设计不变、错误分类及单次失败不自动重试。
- 前端测试：126 passed。
- 真实浏览器、本地模拟接口：两种模式的失败保留原文、长对话分批、手动恢复、窄屏、语言来回切换及设计数据不变通过。
- 既有工作台语言切换、维护者分析正文翻译及原文/JSON/草稿保护通过。
- 2050 段文本及 10 个属性的缓存压力检查通过；86 次批次请求，无循环翻译。

验证未调用线上付费 API，不能据此判定线上密钥、余额和网络状态。部署需要同时更新前端和后端，无需新增环境变量。

## 后续项目审阅

进一步修复：

- 工作台和维护者界面都逐项检查译文类型、空值和目标语言，避免对象被拼接成 `[object Object]`，或长文本中某段空值被悄悄省略。
- 工作台在每批翻译请求前后核对设计及语言版本。切换语言或设计后，旧任务不能再发后续批次，也不能返回旧结果。
- 翻译接口先检查服务商响应结构；空响应、异常字段类型和未完成响应以安全的翻译校验错误返回。
- 经验提炼用量记录优先使用问题轮的 `reported_mode`，旧记录缺少该字段时才回退到提交时模式；保留既有阶段归属。
- 同步页面脚本缓存版本与前端契约测试，修复首次全量回归中发现的旧版本断言失败。

复核确认：经验提炼仍默认优先 DeepSeek（配置可覆盖），跨服务商回退共享 10 次持久化尝试上限；结构校验失败不进入递归修复；审阅通过的经验才参与检索。两种模式使用共同链路。

补充验证：前端 143 项通过；翻译、计费、诊断与服务商回退专项 114 项通过；所有页面本地资源引用存在，Python 编译、全部前端脚本语法和 Git 差异检查通过。浏览器检查涵盖两种模式的翻译失败恢复、维护者原始证据/JSON/草稿保留、手动切换 DeepSeek、10 次上限显示和缓存压力场景。

最终全量回归：1488 passed，212 subtests passed（313.79 秒）。没有调用线上付费模型，也没有执行提交、推送或线上部署。
