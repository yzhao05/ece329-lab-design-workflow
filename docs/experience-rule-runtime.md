# 受控经验规则、审阅草案与隔离回放

本次提供 Guided/EMVR 共用的最小执行闭环：用户语义明确表示不执行旧候选、保留已保存设计并继续时，结束未提交候选，重新检查阶段，并在正文提出下一步问题或通过原有检查推进。不是任意自然语言修补代码的平台。

## 规则与权限边界

旧经验 JSON 不变，继续作为建议；没有自动推断执行动作、前置条件或验证结果的迁移。可执行经验额外包含 `execution`。规范模板由 `experience_rules.contract()` 提供，包含版本、语义意图、四类例外、四个执行环节、动作与参数、前置条件、结果断言、冲突策略、执行/修正上限和正反例。模式/阶段仍为原规则字段，范围继续由审阅接口审批。

当前兼容 v1，并提供 v2 受控动作库。`experience_actions.configurable_contract()` 增加结构化条件和有边界的参数配置；必要的安全动作顺序不能删除或颠倒：

- `decline_uncommitted_candidate`：源文本覆盖完整本轮，模型明确给出 KEEP_CURRENT + ADVANCE，置信度达标，没有新修改或未解析动作，且确有未提交候选。
- `recheck_stage`：复用 `WorkflowEngine._validate_completion`。
- `advance_if_complete`：由原状态机执行，推进前再检查；不直接写阶段编号。
- `ask_missing_fields`：必要行为；校验失败后使用本地阶段/缺项处理器生成具体待办，不让模型凭空补写缺项。旧版 JSON 即使未列出此动作，`ensure_next_task` 也承担此要求。执行计划统一规范化，前端不再提供无效的关闭开关。
- `ensure_next_task`：最多一次本地修正，用已完成动作和有效待办重新构造回复。支持 `status_and_task`（已完成动作＋任务）和 `task_only`（只显示当前任务），不把新的问题追加到无法验证的旧要求后面。

条件编辑器可限制待办类型及至少重复次数（0–10）。明确拒绝未提交候选、要求继续、本轮无新修改仍是不可削弱的前提。`trigger` 是说明，程序只执行展示出的结构化条件。额外文字限制必须由维护者确认已纳入检查，不能转换的内容进入 `unmapped_conditions`；非空时禁止批准执行，或去掉 execution 保留为建议。未知动作依旧报需要代码维护。关闭任意已回答待办、补答任意遗漏问题尚未开放。

任意代码、SQL、未知函数/动作、额外参数、删除例外、削弱前置条件或扩大次数上限均被拒绝。尚未支持通用的“凭回答证据关闭任意重复待办”等动作；尝试添加时返回需要代码维护，而不是声称已经实现。内置的明确拒绝旧候选处理继续保留；回放基线可能已经正确，这时不得把相同行为全部归功于规则。

四个统一检查点为意图判断后、待办处理前、推进前和回复保存前。待办变更同时更新对话主记录、设计状态投影和 carried context。验证检查旧候选结束、既有内容保留、历史保留、阶段检查、具体任务及不重复旧问题。验证破坏既有内容时在最终保存前失败关闭，保留数据库中的已提交设计。

同一轮只完成一次意图适用选择，同一规则 ID/版本/业务状态单轮最多执行一次，回复最多修正一次。会话守卫保留最近 16 个“规范化执行动作＋业务状态”指纹；检索顺序、主规则 ID 或规则说明变化不能重启相同修正，实际候选或设计内容变化仍可正常处理。兼容旧 ID/版本守卫；守卫命中时停止经验自动修正，保留用户意图走原有受约束基础流程。冲突只比较规范化后的执行部分，示例和说明不参与比较。不同写入契约冲突时阻止经验修正；相同契约合并执行并保留全部来源 ID/版本。执行前重新检查所有来源的启用版本。反馈提炼仍沿用原 10 次总尝试上限。

## 审阅操作

1. 填写原不当内容、人工修正内容、处理意见；无需修改时前两项可留空。
2. “根据审阅意见生成修订草案”复用已配置的经验提炼提供商，只调用一次模型，不自动重试。请求用量计入该反馈原有用量统计；未知用量仍为 null。
3. 草案和变更字段独立展示。只有明确点击应用才复制到 JSON 编辑器。生成期间手动改过 JSON 时，必须手动合并或再次明确选择替换；当前生效版本始终不变。
4. 可执行规则先点击“隔离回放当前 JSON”。验证 ID 绑定来源版本、完整 JSON 和 scope；修改任何一项后旧验证不能用于批准。
5. 核对“实际执行条件”，勾选确认没有遗漏的文字限制，然后“启用经验”或“批准修订并启用”。接口同时检查完整 JSON、范围、版本、覆盖充分性及条件确认。停止和并发审批也使旧草案版本失效。恢复历史版本只生成草案，仍需检查、回放及批准，不撤销过去的用户设计修改。

记录刷新、展开收起、语言切换保留当前页面审阅草稿。维护者令牌不保存。生成过的草案另有后端审计记录。原始 JSON、输入框和原始证据不被界面翻译改写。

每条经验顶部提供“导出经验与上下文（JSON）”，待审阅、已启用、已停止以及兼容的旧状态均可使用，Guided/EMVR 共用。导出当前已加载的后端版本，文件名包含经验 ID 和版本；包含接口已提供的经验内容、关联反馈、前后对话、状态快照、分析诊断、截图数据、审阅记录、用量及回放/评测记录。保留缺失与截断标记，不补写未记录上下文；回放/评测历史仍以当前接口提供的范围为准，不是整个数据库备份。未提交的 JSON 编辑和审阅草稿不混入导出，界面翻译也不改变导出原文。

导出只在浏览器本地创建 JSON 文件，不另调模型、不保存审批、不发送维护者令牌到文件。原始 JSON 区域的下载按钮复用相同下载逻辑。可使用 `tools/verify_experience_export_browser.cjs` 运行拦截全部网络请求的浏览器夹具，验证双模式、三种状态、中英文按钮、草稿保留及窄屏；需要 Playwright 和本地浏览器。

## 检索、预算与记录

先过滤启用状态、模式、阶段和权限范围；关键词/类别排序结合候选修改和重复待办的结构化状态，不再按更新时间兜底。受支持语义意图由既有模型解析，跨语言只影响模型输入理解，后端执行判断使用相同结构化动作，不用“继续”等关键词修改状态。第一版不引入向量索引，不能保证任意旧建议都能跨语言召回。

| 配置 | 默认 | 上限 |
|---|---:|---:|
| ECE329_EXPERIENCE_MAX_CANDIDATES | 8 | 20 |
| ECE329_EXPERIENCE_TOKEN_BUDGET | 4096 | 16000 |

预算使用完整规则 JSON 的 UTF-8 字节数作为保守 token 上界，而非声称测得精确 tokenizer 数量。相关内置指导（FB01 等）优先保留，与新增经验共同计入数量和 token 预算，并按 ID 去重。检索与提示组装复用同一个预算函数；被排除的经验不进入执行器。超预算时整个规则排除，绝不删除例外以保留动作。记录相关性、范围、数量、预算及冲突排除原因；最多 120 条检索明细，另记录所有原因计数和省略明细数。

维护者“经验执行记录”展示检索 → 实际注入 → 适用判断 → 动作 → 状态变化 → 验证。实际注入要求本次请求顶层 `feedback_guidance.rules` 包含完整且一致的候选规则；用户引用、历史记录、诊断中的 ID、被截断的规则或不同版本均不计为注入。兼容意图 JSON 和生成请求的 `CONTEXT_JSON` 格式，不保存请求原文。没有用模型时不会伪造注入。默认显示简短结论，技术详情收起，可跳回规则审阅/停止。固定中英文映射不翻译证据。审批、注入、模型声称采用、程序断言通过是不同事件；目前未采集模型的“声称采用”，记 null。

## 回放与限制

固定隔离套件含两种模式、中英文、完整/缺项及四类反例共 264 个场景，覆盖全部 13 个内部阶段；有附加条件时再增加条件不满足的反例。每个声明的模式×阶段至少需要 2 个应触发且实际执行的正例、8 个不应触发的反例。报告分别保存声明范围、测试范围、执行数量、通过数量和未覆盖范围。无正例或反例不足返回 `insufficient_coverage`，不能审批。执行失败与覆盖不足分别记录，不因其他阶段通过而替代未覆盖范围。

执行器回放运行真实工作流代码、内存设计库和模拟语义响应；不调用在线模型、不写真实设计、不导出文件或触发部署。旧 Guided 子阶段归并回想法完善不算向前推进；向前推进必须经过实际的推进前检查。

验证记录同时绑定验证器版本。升级后，旧验证器的结果仍保留用于审计，但不能用于新的审批，必须重新回放。历史状态没有旧候选时按不适用处理，不误报执行失败；损坏或不完整快照标记无法完整回放。

新轮次保存发生前的必要会话状态及语义解析结果；不保存鉴权令牌、服务商上下文或缓存。历史中的 replay 字段不递归复制，也不进入常规回复生成提示词，避免重复带入旧状态与旧语义；原始历史和回放证据仍保留。快照超过 96 KB 或包含凭据字段时记录不可回放原因，不截断后声称完整。缺失问题前快照或当时语义响应的旧记录明确为无法完整历史回放，不使用提交时快照替代。

普通历史回放使用已记录语义响应和本地响应生成器，属于“记录响应隔离回放”，不是真实模型重跑。固定模拟套件通过不代表自定义正反例通过模型语义评测。

维护者可点击“运行真实模型语义评测及隔离流程回放”。此操作使用已配置经验模型，包含全部自定义示例、额外中英文边界反例，在每个声明模式的第一个声明阶段构造测试上下文；不会把人工正确标签发给模型。每个来源版本最多 3 次（失败也计入），每次 1 个请求、最多 8192 输出 token，输入最多 64 KB，不自动重试。输出需保留原文引用并通过形状检查；用量计入反馈，未知值保持 null，评测不消耗反馈提炼的十次额度。

三层结果分别展示：执行器测试、实际模型语义评测、历史完整流程回放。最后一项需要问题发生前真实快照，使用本次真实模型分类结果进入隔离工作流，回复由本地工作流及受控渲染器产生；这不是生产 Agent 所有请求的完整在线重跑。缺历史快照为 unavailable，不适用为 not_applicable；未触发真实模型时为未测试。完整前后对比和每个自定义案例保存在评测详情。规则内容变化后旧评测不得作为当前版本的结果。当前本地验证使用模拟提供商，未消耗真实 API 额度。

维护端执行记录增加最近 1000 轮统计，按规则 ID、版本、模式分别展示检索/条件/执行/验证失败原因计数；通过率仅为已执行验证的断言通过率，不是模型质量或检索成功率。

## 部署

初次实现的后端全套 1557 项测试及 212 个子测试通过；后续审阅的结果见 `review-experience-rules-2026-09-22.md`。真实浏览器夹具验证了草案生成、JSON 冲突提示、刷新保留审阅内容、中英文切换、回放批准及窄屏布局。浏览器夹具使用模拟提供商，未测试线上模型或生产部署。修订草案费用计入原反馈，但不会用于补足缺失的历史分析尝试用量。

后端启动自动新增 `experience_drafts`、`experience_validations` 和 `experience_evaluations`，保留旧经验内容、状态、版本和审阅记录。验证器已升级为版本 4，新审批必须重新回放并确认条件。无需清空数据库。数据库仍应位于持久磁盘；正式更新前备份 SQLite。同步部署后端和 docs 前端。

新增两项检索配置有默认值，不设置也能运行。草案生成复用现有经验模型/API 配置，不需要新 Agent 或新密钥。GitHub Actions 已加入新前端脚本检查；main 的 CI 和容器检查通过且配置 `RENDER_DEPLOY_HOOK_URL` 后，现有部署任务才会触发后端更新。Git push 本身不代表已完成部署。

CMD 中先检查改动，再提交本次文件（不要把不相关的根目录未跟踪文件加入）：


部署后在维护页加载规则 → 生成草案 → 核对 JSON/范围 → 回放 → 批准新版本，然后在原设计明确发送保留并继续的请求，并检查本轮“执行断言通过”记录；仅看到“已启用”或“实际注入”不足以确认修复。
